# Step reference

Generated from `workflows/*.yaml` and `map.yaml` by `tools/docs.py`. Do not edit by hand.

Step ids are written `workflow.step`. Owner is the workflow owner unless a step says otherwise.

**System entry:** `define.intake` — where the PM's input enters. **System exit:** `deliver.done` — where the finished result leaves.

## Foundation  (`foundation`, group: Foundation)

**Owner:** PM  
**Purpose:** Fix the ground rules the system must build within: the architecture file and the glossary. Entered from Define, never directly.  
**Starts when:** Define sorts a request as needing the foundation, either because no architecture file exists yet or because the request needs a tool, language or rule the architecture does not allow  
**Entry step:** `foundation.new-or-change`

### `foundation.new-or-change` — New product or rule change?

Type: decision. Owner: AI. Labels: ENTRY.

Picks the case from the request's change record: no architecture file yet means a new product; otherwise one rule of an existing product must change and be checked against the code already built.

Notes: Every step of this workflow writes its output to disk before the next step starts. When in doubt (a file exists but is empty or belongs to another product), the AI treats it as a rule change, never as a fresh start that could overwrite an existing file, and says so.

Comes from:
- `define.to-foundation` Set or change the foundation first (handoff from another workflow)

Goes to:
- `foundation.architecture` Write the architecture file — when new product, no architecture file yet
- `foundation.propose-rule` Propose the changed rule — when rule change on an existing product

### `foundation.architecture` — Write the architecture file

Type: step. Owner: PM. Labels: PM INPUT.

PM provides: The architecture file, written or pasted by the PM. On a later pass: the file revised for the findings, a finding marked "accepted as is", "the foundation is not needed after all", or "stop".

Produces: The file as written, and the PM's accepted findings, in the record

PM writes or pastes the architecture file. It must cover: the tools, language and resources the system builds with; the rules (including security, accessibility and performance rules, which are otherwise never checked); how the product is run; the systems the product has (frontends, backends, services) and the folder and component convention for each; the environments; where environment variables and secrets live and how the PM supplies them; and the things the system must never do (files never to touch, actions never to take). It is not generated by the system; it can be copied from elsewhere.

Comes from:
- `foundation.new-or-change` New product or rule change? — when new product, no architecture file yet
- `foundation.check` Architecture file complete and consistent? — when findings the PM must resolve

Goes to:
- `foundation.check` Architecture file complete and consistent?

### `foundation.check` — Architecture file complete and consistent?

Type: decision. Owner: AI.

Produces: Findings the PM must resolve, written into the record, if any; a decision entry for each finding the PM accepted as is

A second, independent AI pass reads the file for the required content above, internal contradictions, tools the AI cannot actually reach, and content that belongs to another product. Findings go back to the PM with the file; a finding the PM has marked "accepted as is" is not reported again and is logged as a decision with the PM's reason. The PM's "not needed" or "stop" is routed here.

Notes: When in doubt whether something is a finding, it is reported; the PM can accept it as is. A check that finds nothing on a first-time file is run once more with a different framing (as the builder who must run it; as the reviewer looking for what is missing).

Comes from:
- `foundation.architecture` Write the architecture file

Goes to:
- `foundation.architecture` Write the architecture file — when findings the PM must resolve
- `foundation.glossary` Write the glossary — when complete and consistent
- `foundation.not-needed` Continue without a foundation change — when PM says the foundation is not needed after all
- `foundation.drop` Drop the request — when PM stops

### `foundation.glossary` — Write the glossary

Type: step. Owner: PM. Labels: PM INPUT.

PM provides: The product's terms, one meaning each, from the PM

PM lists the terms and things the product deals with, one meaning each, so every piece of business logic uses the same words. A later change to a term's meaning is a cross-cutting logic change, made in Define.

Comes from:
- `foundation.check` Architecture file complete and consistent? — when complete and consistent

Goes to:
- `foundation.save` Save the foundation

### `foundation.save` — Save the foundation

Type: step. Owner: AI.

Produces: Architecture file and glossary, saved with history; one decision entry per rule that had an alternative (hosting, data store, auth, framework), category by what it governs

Architecture file and glossary are saved with their history. Every rule in the file that was chosen over an alternative becomes a decision entry with the PM's reason, so a later rule change brings the original reason forward; a rule with nothing weighed against it stays only in the file.

Comes from:
- `foundation.glossary` Write the glossary

Goes to:
- `foundation.foundation-only` Was the request the foundation itself?

### `foundation.foundation-only` — Was the request the foundation itself?

Type: decision. Owner: AI.

The very first request of a product is often "here is the architecture"; then there is nothing to discuss and the record is closed as delivered. Otherwise the request that needed the foundation continues.

Comes from:
- `foundation.save` Save the foundation

Goes to:
- `foundation.done` Foundation handled — when the request was the foundation itself
- `foundation.ready` Return to the discussion — when the request still needs logic

### `foundation.ready` — Return to the discussion

Type: handoff. Owner: PM. Labels: EXIT.

Produces: The record, the architecture file and the glossary, handed to Define

The discussion continues with these as its inputs.

Comes from:
- `foundation.foundation-only` Was the request the foundation itself? — when the request still needs logic

Hands off to: `define.discuss` Discuss the capability in *Define business logic*.

Goes to:
- `foundation.done` Foundation handled

### `foundation.propose-rule` — Propose the changed rule

Type: step. Owner: PM. Labels: PM INPUT.

PM provides: The changed rule, written by the PM. On a later pass: the rule revised for the findings, a finding marked "accepted as is", "not needed after all", or "stop".

Produces: A proposed rule, unsaved, written into the record, alongside the active decision it would alter

PM writes the changed rule. Before anything else the AI brings forward the active decision behind the current rule: its situation, decision and reasons, side by side with the proposal. It is a proposal, not yet part of the architecture file: it is written into the file only when the delivery that satisfies it is accepted, and discarded if that delivery is dropped.

Comes from:
- `deliver.back-to-foundation` Return the rule to Foundation (handoff from another workflow)
- `foundation.new-or-change` New product or rule change? — when rule change on an existing product
- `foundation.check-rule` Proposed rule consistent with the file? — when findings the PM must resolve

Goes to:
- `foundation.check-rule` Proposed rule consistent with the file?

### `foundation.check-rule` — Proposed rule consistent with the file?

Type: decision. Owner: AI.

Produces: Findings the PM must resolve, written into the record, if any

A second, independent AI pass checks the proposal against the rest of the architecture file: contradictions, tools the AI cannot reach, required content it would remove. A finding the PM has marked "accepted as is" is not reported again. The PM's "not needed" or "stop" is routed here.

Notes: When in doubt whether something is a finding, it is reported. A check that finds nothing on a rule that touches existing code is run once more with a different framing. When the proposal removes a rule, the check also writes the impact section Define uses for a removal, against the delivered nodes that rely on the rule: each dependant with its source (code tags, logic tree, decision log), what stops working for a user, the options (retire it too, keep it by a replacement, narrow the removal, postpone) with one recommendation and its reason, and any stored data with keep, migrate or delete, never defaulted to delete. The PM chooses at propose-rule, the existing gate, and the choice is recorded as a decision.

Comes from:
- `foundation.propose-rule` Propose the changed rule

Goes to:
- `foundation.propose-rule` Propose the changed rule — when findings the PM must resolve
- `foundation.impact` Send the proposal for an impact check — when consistent
- `foundation.not-needed` Continue without a foundation change — when PM says the rule is not needed after all
- `foundation.drop` Drop the request — when PM stops

### `foundation.impact` — Send the proposal for an impact check

Type: handoff. Owner: PM. Labels: EXIT.

Produces: The proposed rule in the record, handed to Deliver

Delivery finds every piece of code the rule touches and returns a plain-language plan; the PM decides there whether to apply the rule, revise it, or drop it. Once applied, or if it is dropped, the record continues in Define.

Comes from:
- `foundation.check-rule` Proposed rule consistent with the file? — when consistent

Hands off to: `deliver.trace` Trace the affected code and reusable components in *Deliver code*.

Goes to:
- `foundation.done` Foundation handled

### `foundation.not-needed` — Continue without a foundation change

Type: handoff. Owner: PM. Labels: EXIT.

Produces: The record, unchanged foundation, handed back to Define

The discussion continues within the current rules.

Comes from:
- `foundation.check` Architecture file complete and consistent? — when PM says the foundation is not needed after all
- `foundation.check-rule` Proposed rule consistent with the file? — when PM says the rule is not needed after all

Hands off to: `define.discuss` Discuss the capability in *Define business logic*.

Goes to:
- `foundation.done` Foundation handled

### `foundation.drop` — Drop the request

Nothing was saved; the record is closed as dropped.

- `foundation.check-rule` Proposed rule consistent with the file? — when PM stops

## Define business logic  (`define`, group: Business side)

**Owner:** PM  
**Purpose:** The one door every message from the PM enters. Sorts it into the right next step, and for business logic turns it into one approved node (or node set) with acceptance criteria the PM has confirmed, stored on the business side only.  
**Starts when:** The PM says anything to the system — an idea, a new capability, a change, a bug, a question, a queue instruction, a document such as a PRD, or a request received from anyone (the AI may also add a request, marked as its own)  
**Entry step:** `define.intake`

### `define.intake` — State the idea or request

Type: step. Owner: PM. Labels: ENTRY, PM INPUT.

PM provides: The request in the PM's own words. For a bug, what was seen and where. Every PM message is an intake, including an answer at a gate that carries a new request inside it, and including "just fix the typo".

Produces: A change record is created for the request the moment it is stated (named by date, number and a short slug), with a status line naming the current step, who it waits on, and since when; the queue lists all records in order.

PM states what is wanted: a new capability, a change to existing logic, a bug against delivered logic, a dependency patch or a refactor that keeps behaviour, a question about the product or its status, a queue instruction (cancel, reorder), a document (a PRD, notes) holding several of these, or a request received from someone else. A document is split by the AI into one record per request, listed back to the PM to order.

Notes: Every step of this workflow writes its output to disk before the next step starts, so work resumes from the last completed step after any interruption. A message that arrives while the AI is mid-execution is taken in as an intake and queued; a "stop" is honoured at the next task boundary.

Comes from: the workflow trigger.

Goes to:
- `define.sort` What kind of request is this?

### `define.sort` — What kind of request is this?

Type: decision. Owner: AI.

Produces: The kind chosen, the reason, and the lane (small or full), written into the record's state

The AI reads the architecture file and searches the logic tree and the queue, then sorts the request and writes why. The sort reason also states two flags that do not route: whether the request is large (it names several capabilities, several user roles, or a whole product) and whether it is breaking (it names a delivered node or rule that others depend on, or removes one; "no dependants found (tags, tree, glossary)" when it removes something nobody depends on). Both flags feed the discussion. The PM overrules the sorting at the first PM step of the chosen path: settled (a question), confirm-exists, discuss (which can redirect to any other path), the Foundation input step (which can say "not needed"), or deliver.approve-plan.

Notes: When in doubt the AI chooses the path with more PM gates and says why: build over question, logic over fix, foundation over logic. Where two kinds both apply (new logic that also needs a rule), the foundation path wins; the logic follows once the rule is in. A change to the meaning of an existing glossary term is a cross-cutting change to every node that uses it. A bug is sorted as a fix when the AI can name the delivered criterion the symptom violates; the PM need not name it. Lane: "small" when the request touches one existing node, adds no component and needs no rule; otherwise "full". A small lane keeps every gate but runs each challenge once and keeps the plan to one paragraph.

Comes from:
- `define.intake` State the idea or request
- `define.settled` PM settled? — when this is a request to build; sort it

Goes to:
- `define.answer` Answer from the business side — when a question (what does the product do, where is a request, why does it behave this way, is this in scope, show me the product) or a queue instruction (cancel or reorder a waiting request)
- `define.confirm-exists` PM confirms it already exists? — when the logic already exists as a node
- `define.discuss` Discuss the capability — when new logic, a change to an existing node, or a cross-cutting change to several nodes
- `define.to-foundation` Set or change the foundation first — when no architecture file yet, or the request needs a tool, language or rule the architecture does not allow
- `define.to-fix` Send the fix straight to delivery — when existing logic and unchanged criteria — code wrong (the AI can name the violated criterion), a dependency patch, or a refactor that keeps behaviour

### `define.answer` — Answer from the business side

Type: step. Owner: AI.

Produces: The answer with its source named (node, record, rule, glossary term, or the framework's own scope), or the queue change made; written into the record

The AI answers only from what is written: the logic tree and its index, the change records and queue, the decision log (first, for "why"), the architecture file, the glossary, and the framework reference for questions about scope. If the answer is not there, it says so instead of guessing. "Show me the product" runs it using the architecture file's run instructions. A queue instruction (cancel a waiting request, change the order) is applied and confirmed.

Comes from:
- `define.sort` What kind of request is this? — when a question (what does the product do, where is a request, why does it behave this way, is this in scope, show me the product) or a queue instruction (cancel or reorder a waiting request)

Goes to:
- `define.settled` PM settled?

### `define.settled` — PM settled?

The PM confirms the question is settled, or turns it into a request, which is re-sorted. A follow-up question is a new intake.

Produces: The change record, handed to Foundation; its status now walks through Foundation and, for a rule, Delivery

Foundation is written (new product) or a rule change is proposed and impact-checked. One record, one status line, wherever it is.

### `define.to-fix` — Send the fix straight to delivery

Type: handoff. Owner: PM. Labels: EXIT.

Produces: The change record, handed to Deliver. For a bug: the node id, the violated criterion and what was seen. For a patch or refactor: what changes underneath, the statement that behaviour is unchanged, and the nodes served by the code it touches.

The logic is not in question, so no Define pass. Delivery traces the code and plans the fix; every PM gate in Deliver still applies, and the PM can send it to Define from there if it turns out to be a logic change.

Comes from:
- `define.sort` What kind of request is this? — when existing logic and unchanged criteria — code wrong (the AI can name the violated criterion), a dependency patch, or a refactor that keeps behaviour
- `define.discuss` Discuss the capability — when the logic is unchanged; it is a fix

- `define.handed-over` Handed over; the record continues in Foundation or Delivery

### `define.discuss` — Discuss the capability

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: What the product must do, for whom, where it sits in the tree, what must be true to call it working; for a cross-cutting change, which nodes it touches. Or a correction of the sorting: it is a fix, it already exists, it needs the foundation, or stop.

Produces: Discussion notes appended to the record

PM and the AI talk it through (a page or capability, then its sub-flows, e.g. login page > logout, forgot password). Inputs: the architecture file, the glossary, and for a change the current node(s). The discussion is where the PM redirects a wrongly sorted request. When the sort reason flagged the request as large, the discussion ends with a proposed breakdown; when it flagged it as breaking, with the repercussions shown before anything is written. A small request never sees either.

### `define.breakdown` — Propose the chunks

Type: step. Owner: AI.

Produces: A breakdown section in the record: the chunks (one line each, in the PM's words where possible), what each depends on, why each line is there, the recommended order with one reason per position, why it is not split further, and the alternatives considered. A rewrite appends a new proposed block; the old one is never edited.

The AI reads the discussion notes, the architecture file, the logic tree and the glossary and writes the breakdown it proposes. On a later pass it rewrites from the PM's words at the gate (merge, split, reorder, drop) and appends the new proposal under the old one.

Notes: Propose a split when the discussion names more than one capability, more than one user role, or a whole product; when in doubt propose one and let the PM say "one thing". Every chunk is a capability a user could see delivered on its own; a purely technical layer is folded into the capability that first needs it. Order: dependencies first; among independent chunks, the one that de-risks the rest (a rule, a shared term, an integration) before the one with most user value; every position carries its reason. More chunks than the PM can hold in one reading means the request is a document: say so and offer the PRD path (one record per request, no group). Two chunks touching one node share an explicit dependency; the second waits for the first's delivery. Foundation first: a whole-product request with no architecture file goes to Foundation as today; this step is refused until the architecture file exists, and the breakdown is proposed only when Foundation has returned to discuss.

Comes from:
- `define.discuss` Discuss the capability — when several capabilities; propose the chunks
- `define.confirm-breakdown` PM confirms the chunks and their order? — when merge, split, reorder or drop chunks; rewrite from the PM's words
- `define.confirm-impact` PM chooses per dependant? — when a chosen treatment needs a replacement built first; make the set chunks, replacement before removal

Goes to:
- `define.confirm-breakdown` PM confirms the chunks and their order?

### `define.confirm-breakdown` — PM confirms the chunks and their order?

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: PM's yes to the chunks and the order; or, in words, which chunks to merge, split, reorder or drop; or "one thing"; or stop. On a revision reopened from a child: yes to the proposed correction, or the change to it.

Produces: The answer, appended verbatim under "Breakdown — PM answer"; a decision entry with the confirmed set and, as "instead of" lines, the proposals and options the PM rejected. A revision supersedes the earlier decision.

PM reads the proposed chunks, the dependencies, the order and the reasons, and the alternatives considered. A yes sends the group to spawn. Words that change the chunks send the record back to the breakdown for a rewrite. "One thing" means the request is written as a single node after all; the proposal stays in the record as history.

Notes: The loop back to breakdown runs at most three times; after the third round only write (one node) or drop are open. The PM's choice is recorded as the decision, with the recommendation as "instead of"; the AI does not re-argue it.

Comes from:
- `define.breakdown` Propose the chunks

- `define.breakdown` Propose the chunks — when merge, split, reorder or drop chunks; rewrite from the PM's words
- `define.write` Write or update the node, or the node set — when one thing after all; write it as a single node
- `define.drop` Drop the request — when PM stops the request

### `define.spawn` — Create one record per chunk

Type: step. Owner: AI.

Produces: One child change record per confirmed chunk, in the confirmed order, each carrying the parent, its chunk number and what it depends on; chunk 1 at the discussion, the others waiting on the chunk they depend on; a group block in the queue; the breakdown decision written.

The AI creates the child records from the confirmed breakdown. Each child's lane is set from its chunk size (small: one node, no component); the parent is always full. On a revision the existing children keep their files and history, new chunks get new files, removed chunks are dropped with the reason, and the order is rewritten; a delivered chunk is never touched.

Notes: Refused when two chunks touch one node without an explicit dependency between them, and when a child's slug collides with an existing record. Children are created only here; a child started by hand is refused.

Comes from:
- `define.confirm-breakdown` PM confirms the chunks and their order? — when yes, these chunks in this order

Goes to:
- `define.broken-down` Broken down; the chunks continue as their own records

### `define.broken-down` — Broken down; the chunks continue as their own records

Reached only from a child record's discussion. The AI writes what building this chunk showed about the split or the order and reopens the parent so the PM confirms the corrected breakdown. Refused for a chunk already delivered.

### `define.impact` — Show the repercussions

Type: step. Owner: AI.

Produces: An impact section in the record: what is removed or changed and what the user loses; every dependant with its source in brackets, what stops working for a user, the options and one recommendation with its reason; the rules and decisions affected; every store of data affected with keep, migrate or delete and a recommendation; and anything suspected but not traceable, listed as possible, unverified.

The AI traces the dependants of the node being removed or changed and writes the impact section from the logic tree, the code tags, the glossary and the decision log. On a later pass it revises the analysis or the options from the PM's words at the gate.

Notes: Dependants come from the logic tree (nodes that name the node or its glossary terms), the code tags (@node) and active decisions; never from memory. A dependant the AI cannot trace to one of these is listed as "possible, unverified". For every dependant the options are: retire it too; keep it by replacing what it needed (a replacement chunk); narrow the removal so it keeps working; postpone. One recommendation, one reason. Stored data affected by the removal is named with the choice keep / migrate / delete, and the PM chooses; "delete" is never the default. Refused while no architecture file exists, and refused while a named dependant's record is in Deliver, until that record closes (one change in flight per node). A rule removal follows the Foundation path, where check-rule writes the same section.

Comes from:
- `define.discuss` Discuss the capability — when this removes or changes something others depend on; show the repercussions
- `define.confirm-impact` PM chooses per dependant? — when revise the analysis or the options

Goes to:
- `define.confirm-impact` PM chooses per dependant?

### `define.confirm-impact` — PM chooses per dependant?

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: PM's choice for every dependant (retire it too, keep it by a replacement, narrow the removal, postpone) and for every store of data (keep, migrate, delete), one line each; or what to revise in the analysis or the options; or stop.

Produces: The answer, appended under "Impact — PM answer", one line per dependant; a decision entry with the confirmed set and, as "instead of" lines, the recommendations the PM overruled. A revision supersedes.

PM reads what is removed, the dependants and their sources, what stops working, the options with the recommendation, and the stored data. The chosen set goes to write as one node set: the removed node marked retired plus each dependant's chosen treatment. When a kept dependant needs a replacement built first, the set becomes chunks with the replacement ordered before the removal, and the breakdown is proposed from it.

Notes: The loop back to impact runs at most three times; after the third round only write or drop are open. The PM's choice is recorded as the decision, with the recommendation as "instead of"; the AI does not re-argue it.

Comes from:
- `define.impact` Show the repercussions

Goes to:
- `define.write` Write or update the node, or the node set — when proceed with the chosen set
- `define.impact` Show the repercussions — when revise the analysis or the options
- `define.breakdown` Propose the chunks — when a chosen treatment needs a replacement built first; make the set chunks, replacement before removal
- `define.drop` Drop the request — when PM stops the request

### `define.write` — Write or update the node, or the node set

Type: step. Owner: AI.

Produces: Draft node(s): description, proposed acceptance criteria, proposed placement in the tree, any proposed glossary additions; or a node marked retired.

The AI writes each node under its stable id, in plain language, from what the PM said, checked against the architecture file. It proposes the placement (an existing parent or a new header, with the reason), proposes a split if the node is too large, and marks a node retired when the capability is being removed. When the record carries an impact answer, the node set is drafted from it: the removed node marked retired plus each dependant's chosen treatment and the chosen handling of stored data. Any product term not in the glossary is proposed as an addition. Where the discussion left a gap, the AI fills it with a stated default listed under "Assumptions" in the draft; at most three gaps become questions, asked one at a time, each with two to four options and a recommended one, in the order scope, then safety, then experience, then technology.

Notes: The id never changes even if the title or the placement does. Code built for a node carries the id as a tag; that is how changes are traced. Every answered question is written into the draft and the record; the PM can veto any default at approve. When the PM's answer that re-entered this step says the draft stands ("no change", "unchanged"), nothing in the draft is changed: only a one-line note under the step heading that it is re-submitted unchanged, then on to challenge.

Comes from:
- `define.discuss` Discuss the capability — when it is business logic; write it
- `define.confirm-breakdown` PM confirms the chunks and their order? — when one thing after all; write it as a single node
- `define.confirm-impact` PM chooses per dependant? — when proceed with the chosen set

Goes to:
- `define.challenge` Challenge the logic

### `define.challenge` — Challenge the logic

Type: step. Owner: AI.

Produces: A findings section in the record (what was found and how it was fixed), the logic delta (what changes against the delivered version, in plain words) and the list of other nodes affected, for the PM

A second, independent AI pass reads the draft, the glossary, the logic tree and the architecture file. It reports ambiguity, criteria that cannot be verified, conflicts with the architecture rules, terms not in the glossary, and a placement that makes the tree harder to read. It also traces the business side: every other node whose text or links the change affects is listed for the PM, and a conflict with an existing node names that node as one the PM must revise next. For a change it writes the logic delta: what the node said before, what it says now. It searches the decision log: a draft that alters an active decision is reported, and that decision (situation, decision, reasons) is put in front of the PM at approve, side by side with the new one. When the record carries an impact section, the challenge compares its dependants against the code tags (@node, every file under code/, tests included), the logic tree and the decision log, and reports every tagged node the section omits as a finding before approve.

Notes: Non-trivial means the draft touches an existing node or has more than one criterion. A challenge that finds nothing on non-trivial work is run once more with a different framing (as a new user; as the owner of the neighbouring nodes; as the verifier who must test it) before the draft goes to the PM; in the small lane it runs once. When the record returns here after a PM revision, the challenge reads only the delta since its last pass plus the parts that delta touches, never the whole draft again.

Comes from:
- `define.write` Write or update the node, or the node set
- `define.approve` PM approves the logic? — when PM changed or added acceptance criteria

Goes to:
- `define.approve` PM approves the logic?

### `define.approve` — PM approves the logic?

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: PM's yes, with the acceptance criteria confirmed as saying what "working" means (adding or removing any); or what to change. For a node set, or to deliver this node together with another waiting node, the PM says so here.

Produces: The answer, written into the record; a decision entry for what was finalised (logic, criteria, placement, glossary additions), superseding any earlier decision the PM chose to change

PM reads the whole draft as a non-technical document: description, acceptance criteria, placement, glossary additions, the logic delta for a change, the findings the challenge caught, the list of other nodes affected, and any earlier decision this would alter, with its situation and reasons. Before the answer is taken, the AI repeats the decision-log search on the final draft's nodes and glossary terms; a hit not already in the findings blocks the gate and returns to challenge. Changing an earlier decision is an explicit yes, never a side effect.

Notes: If the PM both changes criteria and wants other changes, the logic change wins and it goes back to discuss. A changed criterion alone goes back through challenge; that is the one place two PM readings of the same document follow each other, by design.

Comes from:
- `define.challenge` Challenge the logic

Goes to:
- `define.discuss` Discuss the capability — when PM wants changes to the logic
- `define.challenge` Challenge the logic — when PM changed or added acceptance criteria
- `define.commit` Save the business side — when PM says yes
- `define.drop` Drop the request — when PM stops the request

### `define.commit` — Save the business side

Type: step. Owner: AI.

Produces: Approved node(s) and glossary additions, saved with history (a node version each), each node's status set to "approved, not yet delivered"; the logic index regenerated

The node(s) and any approved glossary additions are saved with their history, business side only. Every later version of a node is one entry in that history. A node whose text did not change gets no new version.

Comes from:
- `define.approve` PM approves the logic? — when PM says yes

Goes to:
- `define.to-deliver` Send to delivery

### `define.to-deliver` — Send to delivery

Type: handoff. Owner: PM. Labels: EXIT.

Produces: The approved node or node set, with confirmed acceptance criteria, in the same change record, handed to Deliver

The code side starts from this record; nothing else crosses the boundary.

Comes from:
- `define.commit` Save the business side

Hands off to: `deliver.trace` Trace the affected code and reusable components in *Deliver code*.

Goes to:
- `define.handed-over` Handed over; the record continues in Foundation or Delivery

### `define.drop` — Drop the request

Type: step. Owner: AI.

Produces: Change record marked dropped; draft discarded; dependants returned to waiting; a decision entry with the PM's reason for stopping, superseding every active decision written under this record

The draft is discarded, the change record is closed as dropped, and any request that depended on it returns to waiting. Nothing was saved except the decision to stop and why.

Comes from:
- `define.discuss` Discuss the capability — when PM stops the request
- `define.confirm-breakdown` PM confirms the chunks and their order? — when PM stops the request
- `define.confirm-impact` PM chooses per dependant? — when PM stops the request
- `define.approve` PM approves the logic? — when PM stops the request

Goes to:
- `define.dropped` Request dropped

### `define.handed-over` — Handed over; the record continues in Foundation or Delivery

Type: end. Owner: PM. Labels: EXIT.

Comes from:
- `define.to-foundation` Set or change the foundation first
- `define.to-fix` Send the fix straight to delivery
- `define.revise-breakdown` Send the correction back to the parent
- `define.to-deliver` Send to delivery

Goes to: nothing; the workflow ends here.

### `define.dropped` — Request dropped

Type: end. Owner: PM. Labels: EXIT.

Comes from:
- `define.drop` Drop the request

Goes to: nothing; the workflow ends here.

## Deliver code  (`deliver`, group: Delivery)

**Owner:** AI  
**Purpose:** Turn an approved node or node set, a fix against delivered logic, or a proposed architecture rule into working, verified, component-based code without the PM ever reading code.  
**Starts when:** A change record arrives from Define (approved logic, or a fix) or from Foundation (a proposed rule)  
**Entry step:** `deliver.trace`

### `deliver.trace` — Trace the affected code and reusable components

Type: step. Owner: AI. Labels: ENTRY.

Produces: The list of affected code (new or existing) and of existing components that can be reused, written into the record

The AI reads the architecture file (systems, structure, rules), then compares the business side with the last delivered version. For a node or node set, it finds every piece of code tagged with those ids: brand-new if nothing is tagged yet, otherwise an edit. For a bug, it starts from the node id and the violated criterion in the record; for a patch or refactor, from what changes underneath and the code that uses it. For a proposed rule, it reads every tagged piece against the rule. In every case it also searches the existing components for ones that already do part of the job, so nothing is written twice.

Notes: Node impact comes from the tags, never guessed; rule impact comes from reading the code against the rule. Every step of this workflow writes its output to disk before the next step starts.

Comes from:
- `define.to-fix` Send the fix straight to delivery (handoff from another workflow)
- `define.to-deliver` Send to delivery (handoff from another workflow)
- `foundation.impact` Send the proposal for an impact check (handoff from another workflow)

Goes to:
- `deliver.plan` Write the change plan in plain language

### `deliver.plan` — Write the change plan in plain language

Type: step. Owner: AI.

Produces: In the record: the plan section (for the PM) and the AI section (task list and sources), kept apart under their own headings

Plan section, for the PM, no code inside: what will change for the user, what will not change, the logic delta for a change, what happens to any existing stored data, which existing components are reused and which new ones are created (by their plain names), anything the PM must supply before work can start (a key, an account, a file), any active decision this plan would alter (brought forward with its situation and reasons), and that the result will be verified against the confirmed acceptance criteria of every node it touches; in the small lane this is one paragraph. AI section: the task list in the form "- [ ] T001 [P] [node-id] what, in which file", grouped in the phases Setup, Foundational, one phase per node, Polish, where [P] marks a task that touches different files from every unfinished task and can run alongside them; and, per tool choice, the current documentation consulted as Decision / Rationale / Alternatives with sources, so the code is built the way those tools are used today, not from memory.

Notes: Optional diagram (convention): when the architecture file names archify as a tool, the plan also runs `framework/tools/archify_delta.py render` on docs/architecture.archify.json and, for a change that touches components, `archify_delta.py compare <before.json>`, which writes docs/architecture.delta.html with its receipt docs/architecture.delta.json and lists every removal, linked from the plan section; the diagram is an aid for the PM at approve-plan, never a gate input, and its absence is not a finding.

Comes from:
- `deliver.trace` Trace the affected code and reusable components
- `deliver.approve-plan` PM approves the plan? — when the plan needs revising (the logic and the rule stand)
- `deliver.tasks-done` All tasks done as planned? — when a task cannot be done as planned; the reason is written into the record
- `deliver.passes` Verification passes? — when the plan itself was wrong, or three passes have failed; unfinished code is set aside
- `deliver.accept` PM accepts the result? — when it does not match the approved logic although verification passed; the plan or its tasks were wrong

Goes to:
- `deliver.challenge-plan` Challenge the plan

### `deliver.challenge-plan` — Challenge the plan

Type: step. Owner: AI.

Produces: A findings section in the record (what was found and how it was fixed)

A second, independent AI pass reads the record, the node(s), the traced code and the components, and reports: anything the plan promises that the node and the tags do not justify; anything affected that the plan omits; a new component that duplicates an existing one; sources that are missing or outdated; a coverage table with one row per acceptance criterion (criterion, has a task, task ids) where an empty row is a finding; a plan that alters an active decision without bringing it forward; and any code words in the plan section. When the plan carries an archify Architecture Delta (see the plan step's notes), the pass also runs `framework/tools/archify_delta.py compare` (exit 2 lists the removals) and reports every component or connection marked removed that the plan section does not name. Findings are fixed before the PM sees it.

Notes: Non-trivial means the change touches existing code or more than one criterion. A challenge that finds nothing on non-trivial work is run once more with a different framing (as the user of the changed flow; as the owner of the components touched); in the small lane it runs once. When the record returns here after a revision, the challenge reads only the delta since its last pass plus what it touches.

Comes from:
- `deliver.plan` Write the change plan in plain language

Goes to:
- `deliver.approve-plan` PM approves the plan?

### `deliver.approve-plan` — PM approves the plan?

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: PM's answer: execute (supplying anything the plan asked for); revise the plan; revise the logic; revise the rule; or drop

Produces: The answer, written into the record; on execute, a decision entry for the plan and for each AI choice inside it that adds a dependency or a stored data shape, superseding any earlier decision the PM chose to change; before the answer is taken the AI repeats the decision-log search on the components the plan touches, and a hit not already in the findings blocks the gate and returns to challenge-plan

PM reads the plan section and answers. "Revise the plan" is for a defect in the plan (a wrong word, something forgotten, an empty case); "revise the logic" is for a change in what the product should do and goes to the business side first, never straight into code. "Revise the rule" applies only to a rule record; "revise the logic" only to a logic or fix record.

Comes from:
- `deliver.challenge-plan` Challenge the plan

Goes to:
- `deliver.execute` Execute the change — when yes, execute
- `deliver.plan` Write the change plan in plain language — when the plan needs revising (the logic and the rule stand)
- `deliver.back-to-define` Return to the business side — when the business logic needs revising
- `deliver.back-to-foundation` Return the rule to Foundation — when the proposed rule needs revising
- `deliver.drop` Drop the change — when no, drop this change

### `deliver.execute` — Execute the change

Type: step. Owner: AI.

Produces: Code and tests as components under their system, tagged, uncommitted; each task ticked in the record as it completes

The AI works through the plan's task list one task at a time, ticking each in the record as it is done, so an interruption resumes at the next unticked task. It writes the code and its tests inside the architecture rules and its never-do list, as components under the folder of the system they belong to (frontend, backend, service), reusing the components the plan named and tagging every touched piece with the id of each node it serves. For a retired node, code tagged only by retired nodes is removed.

Notes: A PM "stop" that arrives during execution is honoured at the next task boundary.

Comes from:
- `deliver.approve-plan` PM approves the plan? — when yes, execute
- `deliver.passes` Verification passes? — when a finding is fixable in code, and fewer than three passes have failed

Goes to:
- `deliver.tasks-done` All tasks done as planned?

### `deliver.tasks-done` — All tasks done as planned?

Type: decision. Owner: AI.

Every task is ticked and was done as the plan said. A task that cannot be done as planned (a tool missing, an API different from the documentation, a component that turns out not to fit) stops the work; the AI does not improvise around the plan.

Notes: When in doubt whether a deviation is within the plan, it is not; go back to plan.

Comes from:
- `deliver.execute` Execute the change

Goes to:
- `deliver.verify` Verify against the acceptance criteria — when all tasks done as planned
- `deliver.plan` Write the change plan in plain language — when a task cannot be done as planned; the reason is written into the record
- `deliver.drop` Drop the change — when PM stopped the change

### `deliver.verify` — Verify against the acceptance criteria

Type: step. Owner: AI.

Produces: Test results and a findings section, written into the record

The whole test suite runs, not only the touched nodes' tests, so a regression elsewhere is seen; a criterion with no test is a finding, so an empty suite never passes by default; a test that fails once and passes on rerun is reported as flaky, not counted as a failed pass. A second, independent AI pass checks the result against the confirmed acceptance criteria of every touched node, the architecture rules and its never-do list, and the sources the plan recorded; not against the plan itself. Untagged code and a component that duplicates another are findings.

Notes: A verification that finds nothing on a change touching existing code is the most suspicious result in the system; it is run once more with a different framing (as the user trying to break it; as the owner of the untouched nodes) before it counts.

Comes from:
- `deliver.tasks-done` All tasks done as planned? — when all tasks done as planned

Goes to:
- `deliver.passes` Verification passes?

### `deliver.passes` — Verification passes?

Type: decision. Owner: AI.

Produces: The failed-pass count, kept in the record and reset whenever the record returns to plan

Every acceptance criterion holds and the reviewer has no open finding.

Notes: When in doubt whether a finding is fixable in code, it goes back to plan; the loop never guesses towards "pass".

Comes from:
- `deliver.verify` Verify against the acceptance criteria

Goes to:
- `deliver.execute` Execute the change — when a finding is fixable in code, and fewer than three passes have failed
- `deliver.plan` Write the change plan in plain language — when the plan itself was wrong, or three passes have failed; unfinished code is set aside
- `deliver.accept` PM accepts the result? — when all criteria hold

### `deliver.accept` — PM accepts the result?

Type: decision. Owner: PM. Labels: PM INPUT.

PM provides: The PM's own use of the changed flow, or, when it cannot be used (a background job, an event, a patch, a rule change touching no node), the evidence shown: test output, logs, a recorded run. Then the PM's answer: accept; not matching; changed mind about the logic; changed mind about the rule; or stop.

Produces: The answer, and for "not matching" what was seen, written into the record; on accept, a decision entry if acceptance settled anything the plan left open (it never supersedes; a conflict found here is a finding for the next plan)

The AI runs the product using the architecture file's run instructions and tells the PM, in plain language, where to go and what to try; where nothing can be tried, it shows the evidence instead. The PM judges against the approved node(s) and their criteria; for a rule delivery, against the evidence that every tagged piece still passes its criteria. "Changed mind about the rule" applies only to a rule record.

Comes from:
- `deliver.passes` Verification passes? — when all criteria hold

Goes to:
- `deliver.commit` Save code, tests and record together — when accepted
- `deliver.plan` Write the change plan in plain language — when it does not match the approved logic although verification passed; the plan or its tasks were wrong
- `deliver.back-to-define` Return to the business side — when seeing it changed the PM's mind about the logic
- `deliver.back-to-foundation` Return the rule to Foundation — when seeing it changed the PM's mind about the rule
- `deliver.drop` Drop the change — when PM stops the change

### `deliver.commit` — Save code, tests and record together

Type: step. Owner: AI.

Produces: One code commit: code, tests, the completed change record, the regenerated component index, each delivered node's status set to "delivered" with its version, a lesson appended to the decisions ledger if any, and an accepted rule if any

One commit holds the code, the tests and the completed change record, which names the version of each business node it delivers or, for a fix, the existing version the code now satisfies, plus the regenerated component index (component, system, nodes served). If the change was a proposed rule, the rule is written into the architecture file, as a new entry in its history, in the same commit, and the decision behind the old rule is marked superseded by the new one. Any lesson worth keeping (a pattern that worked, a trap avoided) is written as a decision entry of category process or code; it never supersedes an existing decision, and a conflict it finds becomes a finding for the next plan. The decision index is regenerated and must validate, or the commit does not happen. Waiting records on a node this delivers are re-sorted. "What did we build for this logic" then has one answer.

Comes from:
- `deliver.accept` PM accepts the result? — when accepted

Goes to:
- `deliver.was-rule` Was this a proposed rule?

### `deliver.was-rule` — Was this a proposed rule?

Type: decision. Owner: AI.

A rule change was raised for a request. If that request still needs logic, it continues in Define; if the request was the rule itself, it is closed as delivered here.

Notes: When in doubt, the request continues in Define; the PM can settle it there. For a large rule change split into several records, "still needs logic" is answered no until the last record is delivered.

Comes from:
- `deliver.commit` Save code, tests and record together

Goes to:
- `deliver.resume-define` Continue the request — when yes, and the request still needs logic
- `deliver.done` Delivered — when no (a node or a fix was delivered), or the request was the rule itself

### `deliver.drop` — Drop the change

Type: step. Owner: AI.

Produces: Change record marked dropped (or, for a rule, "rule dropped"); node reverted or rule discarded; set-aside code discarded; a decision entry with the PM's reason for dropping, superseding every active decision written under this record

A node is returned to its last delivered version on the business side, or removed if it was never delivered; a proposed rule is discarded. Any request that depended on this one returns to waiting. The business side never claims behaviour or rules the product does not have.

Comes from:
- `deliver.approve-plan` PM approves the plan? — when no, drop this change
- `deliver.tasks-done` All tasks done as planned? — when PM stopped the change
- `deliver.accept` PM accepts the result? — when PM stops the change

Goes to:
- `deliver.was-rule-drop` Did a request need this rule?

### `deliver.was-rule-drop` — Did a request need this rule?

Type: decision. Owner: AI.

A dropped rule must not silently drop the capability that asked for it: the request continues in Define, where the PM decides to go on within the current rules or to stop.

Comes from:
- `deliver.drop` Drop the change

Goes to:
- `deliver.resume-define` Continue the request — when yes, the request still needs logic
- `deliver.dropped` Change dropped — when no, or the request was the rule itself

### `deliver.back-to-define` — Return to the business side

Produces: The record with the PM's revision, handed to Define

Any unfinished code is set aside. The business side is edited first, goes through challenge and PM approval again, and only then is a fresh plan written.

Comes from:
- `deliver.approve-plan` PM approves the plan? — when the business logic needs revising
- `deliver.accept` PM accepts the result? — when seeing it changed the PM's mind about the logic

Hands off to: `define.discuss` Discuss the capability in *Define business logic*.

Goes to:
- `deliver.returned` Sent back for revision

### `deliver.back-to-foundation` — Return the rule to Foundation

Type: handoff. Owner: AI. Labels: EXIT.

Produces: The record with the PM's revision, handed to Foundation

Any unfinished code is set aside. The PM revises the proposed rule and it comes back for a fresh impact check and plan.

Comes from:
- `deliver.approve-plan` PM approves the plan? — when the proposed rule needs revising
- `deliver.accept` PM accepts the result? — when seeing it changed the PM's mind about the rule

Hands off to: `foundation.propose-rule` Propose the changed rule in *Foundation*.

Goes to:
- `deliver.returned` Sent back for revision

### `deliver.resume-define` — Continue the request

Type: handoff. Owner: AI. Labels: EXIT.

Produces: The record, with the rule now applied or marked dropped, and the current architecture file, handed to Define

The request that needed the rule continues into discussion with the current architecture file and the glossary as inputs; if the rule was dropped, the discussion decides whether to go on within the current rules or stop.

Comes from:
- `deliver.was-rule` Was this a proposed rule? — when yes, and the request still needs logic
- `deliver.was-rule-drop` Did a request need this rule? — when yes, the request still needs logic

Hands off to: `define.discuss` Discuss the capability in *Define business logic*.

Goes to:
- `deliver.done` Delivered

Type: end. Owner: AI. Labels: EXIT.

- `deliver.back-to-define` Return to the business side
- `deliver.back-to-foundation` Return the rule to Foundation

- `deliver.was-rule-drop` Did a request need this rule? — when no, or the request was the rule itself
