# Architecture file

## Definition
The rules the system must build within. Written or pasted by the PM in
`foundation.architecture`; never generated by the system; one per product.
It must cover: the tools, language and resources; the rules, including
security, accessibility and performance rules (an unwritten rule is never
checked); how the product is run; the systems the product has (frontends,
backends, services) with the folder and component convention for each; the
environments; and where environment variables and secrets live and how the
PM supplies them.

## Inputs
The PM's decisions, or a document copied from elsewhere. A change to one
rule enters as a proposed rule at `foundation.propose-rule`.

## Outputs
The architecture file on the business side (`architecture.md`,
**convention**), saved at `foundation.save` for a new product, and updated
at `deliver.commit` when a proposed rule's delivery is accepted.

## How to interact
PM: write it once, when `define.sort` finds no architecture file. To change
a rule, state the need at `define.intake`; sorting sends it to
`foundation.propose-rule`; Deliver shows the impact as a plan; the PM
applies, revises or drops it. Findings from `foundation.check` or
`check-rule` come back to the PM with the file to resolve.
AI: read it at `define.sort` (does it cover the request?), `define.write`
and `define.challenge`, `deliver.trace` (systems, structure, rules),
`deliver.execute`, `deliver.verify`, and for the run instructions at
`deliver.accept`. Check it at `foundation.check` and `check-rule` for the
required content, contradictions, tools the AI cannot reach, and content
from another product. Never edit it except to write an accepted rule at
`deliver.commit`.

## Place in the system
The first thing that exists. Constrains everything written after it,
including how code is organised into systems and components. A proposed
rule is the only input to Deliver besides a change record from Define.

## Optional diagram (convention)
When the PM lists archify (github.com/tt-a1i/archify, an agent skill
that renders a typed JSON description into a self-contained HTML diagram)
among the tools in the architecture file, the AI keeps
`docs/architecture.archify.json` beside `architecture.md` and renders it to
`docs/architecture.html` at `foundation.save` and at `deliver.plan`. At
`deliver.plan` a change that adds, removes or rewires a component also
produces an Architecture Delta (`python3 framework/tools/archify_delta.py
compare <before.json>`, which wraps `archify compare architecture` and writes
`docs/architecture.delta.html` with its receipt `docs/architecture.delta.json`)
of the architecture before and after, linked from the plan section, so the
PM sees the structural effect at `approve-plan` without reading the trace;
`deliver.challenge-plan` reads the receipt and reports any removal the plan
does not name. The JSON is
derived from `architecture.md` and `code/COMPONENTS.md`, never the other
way round; the diagram is an aid, not a gate input, and its absence is not
a finding. Node.js is required only for this option; `archify_delta.py locate` finds the
CLI or prints the install command, and `install_commands.py --with-archify`
installs it with the slash commands.
