# Decision log

## Definition
The structured record of every decision that finalises something, on
either side: product, business, UI, frontend, backend, code, infra,
software, process. One file per decision under `decisions/`, plus a
generated index. A decision is never edited after it is made; a later
decision that alters it *supersedes* it, and the earlier one is brought
forward to the PM before that happens.

## File format (convention)
`decisions/D-0042-<slug>.md`; the id is the filename's first part, so it
is written once. YAML front matter then body:

```yaml
---
made_at: "2026-09-09T14:32+05:30"   # date and time with offset, quoted; the offset fixes the moment
region: India                       # optional: the market or jurisdiction the decision applies to
effective_from: "2026-10-01"        # optional: when it takes effect, if not immediately
category: backend          # product | business | ui | frontend | backend | code | infra | software | process
made_by: PM                # PM | AI (an AI decision is a choice inside an approved plan the PM did not have to make)
at_step: deliver.approve-plan       # the workflow step where it was finalised
record: changes/2026-09-09-3-refund-flow.md   # the change record it belongs to, if any
nodes: [refund-request]    # node ids it concerns, if any
resources: [code/backend/payments/, architecture.md#payments]   # required for made_by: AI (the component or folder it governs)
supersedes: D-0017         # earlier decision it alters, if any; that file gets `superseded_by: D-0042`
links: [https://…]         # tickets, docs, threads
---
# <one-line decision, in plain language>

## Situation
What was the case at the time, in two or three sentences.

## Decision
Exactly what was decided (the description).

## Reasons
Why. Must name at least one rejected alternative, as a line starting
"Instead of …". No alternative, no decision file: a fact with nothing
weighed against it lives in the architecture file or the record, which
already carry history.
```

There is no `status` field: a decision is active unless `superseded_by`
is set. `superseded_by` is the only line ever added to an existing file.

## Inputs
Every step that finalises something where an alternative was rejected:
`define.confirm-breakdown` (the confirmed chunks and their order),
`define.confirm-impact` (the chosen treatment per dependant and per
store of data), `foundation.check` (an accepted finding), `foundation.save` (rules that
had an alternative: hosting, data store, auth; not "the run command"),
`define.approve` (logic, criteria, placement, glossary additions),
`deliver.approve-plan` (the plan; and each AI choice inside it that adds a
dependency or a stored data shape, not a folder name), `deliver.accept`
(only if acceptance settled something the plan left open), every `drop`
(the reason for stopping), `deliver.commit` (a lesson, category `process`
or `code`).

**Breakdown and impact decisions (convention).** Both are `category:
product`, `made_by: PM`, `record:` the request, `nodes:` the chunk slugs
or the removed node and its dependants, and `at_step` the gate that
finalised them: `define.confirm-breakdown` or `define.confirm-impact`.
`## Situation` names the request and the PM's answer; `## Decision` is
the confirmed set (the chunks in order, each with what it depends on and
its child record; or the removed node marked retired and, per dependant,
the chosen treatment, plus keep / migrate / delete per store of data);
`## Reasons` carries one "Instead of …" line per rejected alternative:
for a breakdown, each alternative the proposal considered (a coarser
split, a finer split, a different first chunk) and, when the PM said
"one thing", the split itself; for an impact, each recommendation the
PM overruled ("Instead of retiring `weekly-streak`, as recommended, it
is kept by a replacement"). The breakdown decision is written by
`orchestrate.py` when `define.spawn` runs
(`decisions/D-<nnnn>-breakdown-<parent-slug>.md`); a re-spawn after
`define.revise-breakdown` writes a new one with `supersedes:` and marks
the earlier one `superseded_by:`. The impact decision is written by the
AI at `define.write` from the `## Impact — PM answer` block. Neither is
re-argued: the PM's choice is the decision, the recommendation its
"instead of".

## Outputs
`decisions/D-<nnnn>-<slug>.md` per decision; `decisions/INDEX.md`
generated by `framework/tools/decisions_index.py`: active decisions by
category, and the supersede chains. The generator validates the log as a
contract and fails on: missing fields, a category outside the list, a
`made_at` without time and offset, ids that are not `D-` plus four digits,
a `supersedes` or `superseded_by` that does not point back, a Reasons
section with no "Instead of" line, a `resources` missing on an AI
decision, an empty section, and, when git is present, any change to an
existing decision file other than adding `superseded_by`.

## How to interact
PM: decisions are written for the PM to read later, in plain language;
the PM sees them again whenever one is about to be altered.
AI: **write** a decision file at every finalising step listed above, in
the same save as the step's output. **Before** writing, search the log
for active decisions on the same nodes, the same glossary terms, and the
same components or folders (`resources`); the search is repeated at the
gate itself on the final draft, and a hit not already in the findings
blocks the gate and returns to the challenge. If the new decision alters
one, it is brought to the PM *before* the gate is answered: the earlier
decision's situation, decision and reasons, side by side with the new one,
and the question "do you want to change this?". Only after the PM says
yes is the new decision written with `supersedes`, and the old one marked
`superseded_by`. Decisions written at `deliver.accept` and
`deliver.commit` never supersede anything: a conflict found there is
written into the record as a finding for the next plan, where a PM gate
exists. A `drop` decision supersedes every active decision written under
the same record, so the log never asserts logic the product does not
have. `define.challenge` and `deliver.challenge-plan` report a draft or
plan that alters an active decision nobody brought forward.
`define.answer` answers "why does it behave this way" from this log
first.

## Place in the system
The memory of *why*. The logic tree says what the product does, the
change records say what was built and when, the decision log says why
each of them is the way it is, and stops the PM from reversing a
considered decision without seeing it.
